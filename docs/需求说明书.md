## 1. 项目概述

### 1.1 项目背景

宿舍里存在大量"看情况动手"的重复操作：天黑了开灯、太热了开空调、湿气重了开风扇、人走了关设备。本项目把这些**人工判断**抽象成可编辑的**自动化规则**，由规则引擎根据当前环境数据自动推导设备动作，并完整记录每一次触发的原因与结果，供使用者复盘和调整。

### 1.2 项目目标

构建一个可在 HarmonyOS 设备上真实运行的应用，实现"**定义规则 → 模拟环境 → 观察联动 → 排查冲突 → 保存恢复**"的完整闭环，且所有核心数据在应用被杀死后重新打开仍能恢复。

### 1.3 范围说明

**包含：**

- 4 类可控设备（灯、空调、窗帘、风扇）的状态管理
- 3 项可调环境数据（温度、光照、湿度）与 1 项人体存在状态
- 规则的新增、修改、启停、删除，条件支持单条件与双条件组合
- 规则引擎的真实计算、冲突仲裁、执行日志
- 至少 2 组环境场景的一键模拟
- Preferences 持久化与冷启动恢复
- 覆盖正常/边界/异常的自动化单元测试

**不包含：**

- 真实硬件控制与物联网协议对接
- 云端同步、账号体系、多人协作
- AI 生成规则或自然语言解析规则

### 1.4 术语表

| 术语 | 含义 |
|---|---|
| 规则（Rule） | 一条"条件满足 → 执行设备动作"的自动化配置 |
| 条件（Condition） | 对某一环境指标的比较表达式，如 `温度 > 28` |
| 动作（Action） | 对某一设备某个属性的赋值意图，如 `空调.power = true` |
| 环境状态（EnvState） | 当前模拟的环境指标快照 |
| 仲裁（Arbitration） | 多条规则想改同一设备属性时的优先级裁决过程 |
| 场景（Scenario） | 一组预设的环境指标，用于一键切换模拟条件 |

### 2.2 用户故事

- 作为宿舍用户，我希望夜里光照低于阈值时自动开灯，这样回宿舍不用摸黑找开关。
- 作为宿舍用户，我希望温度高于阈值**且**有人在房间时才开空调，避免空转耗电。
- 作为宿舍用户，我希望人离开后自动关闭灯和风扇，节约用电。
- 作为宿舍用户，当两条规则互相打架时，我希望系统按我设定的优先级执行，并在日志里告诉我哪条被跳过了。
- 作为宿舍用户，我关掉应用再打开，希望之前配好的规则和设备状态都还在。

## 3. 业务规则（规则引擎语义）

### 3.1 环境指标定义

| 指标 | 键名 | 类型 | 取值范围 | 单位 |
|---|---|---|---|---|
| 温度 | `temperature` | number | -10 ~ 50 | °C |
| 光照 | `illuminance` | number | 0 ~ 2000 | lux |
| 湿度 | `humidity` | number | 0 ~ 100 | % |
| 人体存在 | `presence` | boolean | true / false | — |

### 3.2 设备与可写属性

| 设备 | 类型枚举 | 可写属性 | 取值 |
|---|---|---|---|
| 顶灯 | `LIGHT` | `power` / `brightness` | boolean / 0–100 |
| 空调 | `AC` | `power` / `targetTemp` | boolean / 16–30 |
| 窗帘 | `CURTAIN` | `openness` | 0–100 |
| 风扇 | `FAN` | `power` / `speed` | boolean / 1–3 |

### 3.3 计算流程（必须严格按此顺序）

1. **收集**：取出全部 `enabled === true` 的规则，按 `priority` 降序、`createdAt` 升序排序。
2. **求值**：对每条规则计算其条件表达式。
   - `logic === 'AND'`：全部条件为真才算命中；
   - `logic === 'OR'`：任一条件为真即命中；
   - 单条件规则无需区分 logic。
3. **展开**：命中规则的动作展开成"目标属性 → 期望值"列表，并携带来源规则与优先级。
4. **仲裁**：按 `targetKey = deviceId + '.' + property` 分组。
   - 每组取 `priority` 最大者作为**胜出动作**；
   - 优先级相同时，`createdAt` 更早（先定义）的胜出；
   - 落败动作不修改设备，但必须写入日志并标记 `status: 'rejected'` 与 `reason`。
5. **应用**：胜出动作按规则执行顺序依次写入设备状态，记录 `from` / `to`。
6. **记录**：生成一条 `LogEntry`，包含时间戳、参与计算的规则数、命中规则、执行顺序、被拒动作。
7. **持久化**：设备状态、日志（保留最近 100 条）写回 Preferences。

### 3.4 关键判定规则

- **边界语义**：比较符为严格不等号时，等于临界值**不触发**（`温度 > 28`，28.0 不触发，28.1 触发）。
- **幂等**：设备目标值已与当前值相同，动作记为 `skipped`（no-op），不计入变更次数。
- **停用规则**：完全不参与收集阶段，不产生日志噪声。
- **空条件规则**：不允许保存，保存时校验报错。
- **越界输入**：环境值或动作值超出 3.1/3.2 定义范围时，拒绝该输入并提示，不写入存储。
- **启动即计算**：应用冷启动恢复数据后立即执行一次计算，保证界面状态与规则一致。

## 4. 数据模型

### 4.1 实体关系

```
Rule 1 ── n Condition
Rule 1 ── n Action
Rule  ──→ (执行) ──→ LogEntry
Device ──── DeviceState
Scenario ──→ EnvState
```

### 4.2 实体定义

| 实体 | 字段 | 类型 | 约束 |
|---|---|---|---|
| `Rule` | `id` | string | 唯一，时间戳 + 随机串 |
| | `name` | string | 非空，≤ 20 字 |
| | `enabled` | boolean | 默认 true |
| | `priority` | number | 1–10，默认 5 |
| | `logic` | 'AND' \| 'OR' | 默认 'AND' |
| | `conditions` | Condition[] | 长度 ≥ 1，≤ 2（本版本） |
| | `actions` | Action[] | 长度 ≥ 1，≤ 2 |
| | `createdAt` | number | 毫秒时间戳 |
| `Condition` | `metric` | MetricKey | temperature / illuminance / humidity / presence |
| | `operator` | Operator | > >= < <= == != |
| | `value` | number \| boolean | 与 metric 类型匹配 |
| `Action` | `deviceId` | string | 必须是已存在设备 |
| | `property` | string | 必须是该设备可写属性 |
| | `value` | number \| boolean | 落在属性取值范围内 |
| `Device` | `id` | string | 固定 4 台：light / ac / curtain / fan |
| | `type` | DeviceType | 枚举 |
| | `name` | string | 展示名 |
| | `state` | DeviceState | 见 3.2 |
| `EnvState` | 见 3.1 | | |
| `Scenario` | `id` / `name` / `env` | string / string / EnvState | 至少 2 组内置 |
| `LogEntry` | `id` | string | 唯一 |
| | `ts` | number | 时间戳 |
| | `matchedRuleIds` | string[] | 命中的规则 |
| | `steps` | LogStep[] | 按执行顺序 |
| | `rejected` | LogReject[] | 被仲裁拒绝的动作及原因 |

### 4.3 持久化设计（Preferences）

| Key | 内容 | 序列化 |
|---|---|---|
| `app.rules` | Rule[] | JSON 字符串 |
| `app.devices` | Device[] | JSON 字符串 |
| `app.env` | EnvState | JSON 字符串 |
| `app.logs` | LogEntry[] | JSON 字符串，截断至 100 条 |
| `app.scenarios` | Scenario[] | JSON 字符串 |
| `app.version` | number | schema 版本号，用于后续迁移 |

> 选型说明：数据量小（< 100KB）、结构简单，Preferences 足够且启动快；若后续日志量增长，再迁移到 RDB，`RuleRepository` 接口保持不变。

### 5.2 核心接口约定

```ts
// engine/RuleEngine.ets
export interface EvaluationResult {
  steps: LogStep[];        // 按执行顺序的应用结果
  rejected: LogReject[];   // 仲裁中被拒绝的动作
  matched: Rule[];         // 命中的规则
  nextDevices: Device[];   // 计算后的设备快照（不修改入参）
}

export interface IRuleEngine {
  evaluate(env: EnvState, rules: Rule[], devices: Device[]): EvaluationResult;
}

// engine/ConditionEvaluator.ets
export interface IConditionEvaluator {
  test(cond: Condition, env: EnvState): boolean;
}

// repository/RuleRepository.ets
export interface IRuleRepository {
  loadAll(): Promise<AppSnapshot>;      // rules + devices + env + logs + scenarios
  saveRules(rules: Rule[]): Promise<void>;
  saveDevices(devices: Device[]): Promise<void>;
  saveEnv(env: EnvState): Promise<void>;
  appendLog(entry: LogEntry): Promise<void>;
  clearAll(): Promise<void>;
}
```

**约定：** `engine` 层为**纯函数**，不依赖 Context、不读写存储、不弹 Toast，因此可在单元测试中直接调用；所有副作用集中在 `repository` 与 `viewmodel`。

## 6. 异常与边界处理

| 场景 | 处理方式 |
|---|---|
| 环境数值越界（如湿度 150） | 输入即钳制到合法区间并在界面提示"已修正到 100%" |
| 动作为空 / 条件为空 | 保存按钮置灰，给出原因文案 |
| 规则名重复 | 允许，但编辑页提示"已存在同名规则" |
| 目标设备不存在（数据损坏） | 加载时跳过该动作并写日志 `reason: 'device_missing'` |
| 存储 JSON 解析失败 | 捕获异常，回退到内置默认规则，并保留原始字符串到 `app.corrupt.<ts>` 供排查 |
| 日志超过 100 条 | 保留最新 100 条，其余丢弃 |
| 删除唯一规则 | 允许，界面进入"暂无规则"空态引导新建 |
