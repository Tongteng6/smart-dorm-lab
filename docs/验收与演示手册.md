> 用途：自测每一功能是否达标、录屏演示脚本、答辩时按表核对。
> 对应《软件需求说明书》v1.0 与课程期末大作业「主题三」要求。

## 一、这个 App 到底在做什么

一句话：**把「什么情况该开什么设备」写成规则，让引擎根据当前环境自动执行，并把每次执行的原因和结果都记下来。**

三个核心概念：

| 概念 | 含义 | 举例 |
|---|---|---|
| **环境（Env）** | 当前宿舍的状态快照 | 温度 29°C、光照 800lux、湿度 45%、有人 |
| **规则（Rule）** | 「条件成立 → 执行动作」 | 温度 > 28 **且** 有人 → 开空调、设定 24°C |
| **日志（Log）** | 每次计算的过程证据 | 命中几条、按什么顺序执行、谁覆盖了谁 |

引擎每次计算的 6 步（这是整个项目的技术核心）：

```
① 收集启用规则（按优先级降序、创建时间升序）
② 条件求值（AND 全真 / OR 一真）
③ 动作展开（同一设备属性可能被多条规则争抢）
④ 冲突仲裁（优先级高者胜，同级先定义者胜，落败者记录原因）
⑤ 应用变更（记录 from → to）
⑥ 生成日志
```

## 二、界面导览

| 页面 | 进入方式 | 职责 |
|---|---|---|
| **首页** | 启动即是 | 环境模拟（3 滑块 + 1 开关）、设备状态墙、场景快捷入口、最近一次执行摘要 |

| **场景演练** | 底部「场景」 | 一键切换环境、把当前环境存为场景、恢复出厂设置 |

## 三、出厂数据（验收前先看这个）

**环境默认值**：26°C / 500lux / 55% / 有人

**6 条内置规则**：

| 编号 | 规则名 | 优先级 | 条件 | 动作 |
|---|---|---|---|---|
| R1 | 高温开空调 | P8 | 温度 > 28 **且** 有人 | 空调开、24°C |
| R2 | 天黑开灯 | P6 | 光照 < 200 **且** 有人 | 顶灯开、亮度 70% |
| R3 | 潮湿开风扇 | P5 | 湿度 > 70 | 风扇开、2 档 |
| R4 | 人走关设备 | P9 | 无人 | 顶灯关、风扇关 |
| R5 | 白天省电关空调 | P4 | 光照 > 500 **且** 有人 | 空调关 |
| R6 | 离寝关空调 | P9 | 无人 | 空调关 |

> **为什么必须有 R6**：规则引擎是「动作型」——只有规则命中时才执行动作，**设备不会自动复位**。
> 若没有 R6，人离开后空调会保持 R1 打开的状态，看起来就像"无人也一直开着"。

**4 台设备**：顶灯（开关/亮度）、空调（开关/设定温度）、窗帘（开合度）、风扇（开关/档位）

**4 个场景**：白天有人（29/800/45/有人）、夜间归寝（24/60/55/有人）、梅雨潮湿（27/320/86/有人）、无人在寝（30/700/50/无人）

> ⚠️ 设备**没有手动开关**，状态完全由规则计算得出。想看设备动，就去改环境或点场景。

## 四、逐功能验收清单

### F1 环境模拟器 —— 3 项数据可调

| 项目 | 内容 |
|---|---|
| 操作 | 拖动「温度」滑块，从 26 拖到 30 |
| 预期 | 右侧数值**实时**跟着变（26.0°C → 30.0°C），不是卡住的 |
| 验收点 | 三项可调模拟环境数据 ✅ |

**光照**：拖到 500→800，数值实时变；**湿度**：拖到 55→80，数值实时变。

---

### F2 双条件规则生效（R1）

| 项目 | 内容 |
|---|---|
| 前置 | 「有人」开关是**开**的 |
| 操作 | 温度拖到 **30** |
| 预期 | 空调卡片变蓝、角标变绿「开」、文字变「制冷中 · 24°C」；右上角「1 台运行」 |
| 反证 | 把「有人」关掉，温度仍 30 → **R6 命中，空调立即关闭**（证明 R1 依赖「有人」这个条件） |
| 验收点 | 至少 1 条由两个条件共同决定的规则 ✅ |

---

### F3 设备联动（4 类设备都能动）

按顺序操作，观察对应设备：

| 操作 | 触发规则 | 预期设备变化 |
|---|---|---|
| 温度 30 + 有人 | R1 | 空调 **开**，24°C |
| 光照 150 + 有人 | R2 | 顶灯 **开**，亮度 70% |
| 湿度 80 | R3 | 风扇 **开**，2 档 |
| 「有人」关掉 | R4 + R6 | 顶灯 **关**、风扇 **关**、空调 **关** |
| 光照 800 + 有人 | R5 | 空调 **关** |
| 光照 150 + 有人，再新建规则「光照<200 → 窗帘开合度 80」 | 自定义 | 窗帘 **开合 80%** |

> 窗帘默认没有任何内置规则驱动，需要自己建一条才能看到它动——这正好是 F5 的演示素材。

---

### F4 冲突仲裁（本项目最关键的加分点）

| 项目 | 内容 |
|---|---|
| 操作 | 点场景 **「☀ 白天有人」**（29°C / 800lux / 45% / 有人） |
| 触发 | 温度 29 > 28 → R1 命中（开空调）；光照 800 > 500 → R5 命中（关空调）。**两条抢同一个属性 `ac.power`** |
| 预期 | 空调最终是**开**的（R1 优先级 8 > R5 优先级 4） |
| 日志证据 | 进入日志页，可见红色文字：<br>`白天省电关空调 → ac.power = false，被「高温开空调」覆盖：优先级较低（4 < 8）` |
| 验收点 | 冲突有明确优先级处理 + 有可查证的记录 ✅ |

---

### F5 新增规则

| 项目 | 内容 |
|---|---|
| 操作 | 底部「规则」→ 右上「+ 新建」→ 名称填「开窗帘」→ 条件：光照 `<` 200 → 动作一：设备「窗帘」、属性「开合度」、目标值 `80` → 保存 |
| 预期 | 返回列表能看到新规则卡片；把光照拖到 150，窗帘变成「开合 80%」 |
| 验收点 | 新增规则（≥4 条总数满足） ✅ |

---

### F6 编辑规则

| 项目 | 内容 |
|---|---|
| 操作 | 点开 R1「高温开空调」→ 把优先级从 P8 拖到 **P3** → 保存 → 再点「白天有人」场景 |
| 预期 | 这次空调变成**关**的（R5 的 P4 > R1 的 P3），日志里的“谁覆盖谁”反过来 |
| 附加 | 把优先级改回 P8，结果恢复 |
| 验收点 | 修改规则 + 优先级真实影响执行顺序 ✅ |

### F12 持久化恢复（评分表 9 分项，必须录屏）

| 步骤 | 操作 |
|---|---|
| 1 | 新建一条规则（如 F5 的「开窗帘」），把环境调到 30°C / 有人，触发一次联动 |
| 2 | 从模拟器底部上滑，**把应用进程彻底划掉** |
| 3 | 重新打开应用 |
| 4 | 检查：规则还在？设备状态还在？日志还在？环境数值还在？ |

**预期**：四项全部恢复，且启动后立即按当前环境重算一次（界面与规则一致）。

| 用例 | 覆盖类型 | 内容 |

## 五、录屏脚本（建议 6–8 分钟）

录屏是评分依据之一，按这个顺序录，一条不落：

| 时间 | 镜头 | 台词/动作要点 |
|---|---|---|
| 0:00 | 首页 | 「这是联动实验室，用规则自动控制宿舍设备」 |
| 0:30 | 拖温度滑块 | 展示数值实时变化、设备无反应（26→28 未到阈值） |
| 1:00 | 温度拖到 30 且有人 | **空调自动开启**，右上角计数 +1 |
| 1:30 | 开日志 | 展示执行顺序 `#1 高温开空调 → ac.power false→true` |
| 2:00 | 点「白天有人」 | 展示 **R1 与 R5 冲突**，日志里红字说明被谁覆盖 |
| 3:00 | 规则列表 | 逐条讲 4 类设备、6 条规则 |
| 3:40 | 新建规则 | 现场建一条「开窗帘」，验证生效 |
| 4:40 | 编辑优先级 | 把 R1 改成 P3，冲突结果反转，证明优先级真实生效 |
| 5:40 | 启停 + 长按删除 | 展示开关与二次确认 |
| 6:20 | **杀进程重开** | 强调规则/设备/日志全部恢复 |
| 7:10 | 场景页 | 4 组场景逐个点 |
| 7:40 | 跑单元测试 | 12 条全绿 |

> 录屏时把模拟器窗口和 DevEco 的测试结果都录进去，证明「真实运行」。

## 六、常见问题

| 现象 | 原因 / 处理 |
|---|---|
| 拖滑块数字不动 | 未安装最新包（f64fb26 之后才修复），重新 Run |
| 设备卡片一直不亮 | 该设备当前没有规则命中；看日志「命中 0 条」 |
| 状态残留（如一直「无人」） | 场景页 → 恢复出厂设置 |
| 改代码后界面没变 | DevEco 需重新 Run，热重载对 @State 结构改动不可靠 |
